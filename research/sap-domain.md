## 1. Multi-instance SAP + tax engine integration pattern; what "read-only" rules out

**Standard pattern (Vertex O Series, ONESOURCE Determination, Avalara AvaTax — all three):**
The tax engine sits *outside* SAP and is called synchronously at the pricing/tax-determination step inside a live transaction (PO, goods receipt, AP invoice posting). SAP's pricing procedure is configured to call the external engine via RFC (Vertex's classic connector) or REST/API (modern S/4HANA side-by-side extensibility on SAP BTP), the engine returns a jurisdiction + tax code + rate, and SAP writes that result back onto the document. Vertex explicitly maintains per-company-code data ("vendor classes" — vendor code, vendor name, and the company code/taxpayer the vendor belongs to) so one engine instance can serve multiple SAP company codes with different tax profiles. Thomson Reuters ONESOURCE positions the same way: "single centralized tax engine" fed by "pre-built and certified integrations" per ERP, so multiple SAP instances (or company codes within instances) can all point at one engine without being consolidated first.

Key implication: **you don't need to consolidate the three SAP instances to integrate a tax engine.** The pattern was designed for exactly this — multiple source ERPs, one tax brain. This directly undercuts any framing that treats non-consolidation as a blocker to a unified tax layer; it's a solved integration problem, not a structural one.

**What "read access only, no writes, any version" actually rules out architecturally:**
- Standard tax-engine integrations (Vertex, ONESOURCE) are *transactional* — they intercept a live posting and write the determined tax code back onto the SAP document in real time. That write-back is exactly what's forbidden. So the brief's "AI that reads invoices and tells us the right tax treatment" **cannot be built as a live, in-transaction SAP integration** in v1. It has to be built as a side-by-side/read-only extraction-and-advise layer: pull invoice, PO, goods-receipt, vendor-master data out via read-only APIs/RFC/OData (SAP's own side-by-side extensibility model — BTP consuming stable read APIs via "communication scenarios" configured for read-only access), run determination and recovery logic externally, and surface a recommendation to a human — who then makes the actual correction or claim through whatever channel Northgate already uses (manual SAP entry, the tax engine's own workflow, a filing system). The system never posts anything back into SAP itself.
- No writes also rules out any "auto-fix the vendor master" or "auto-correct the tax code in SAP" remediation — consistent with the Head of Tax Risk's veto and the security team's control posture. Correction has to happen through an existing SAP user with their own write permissions, with the tool's output as a recommendation/audit trail, not an autonomous write.
- This is a reasoned inference from how SAP extensibility/communication-scenario permissioning works, not a documented "read-only tax AI" case study — I did not find a public source describing this exact constraint combination (read-only + multi-instance + tax recovery AI). Treat as ASSUMED architecture logic, not a verified vendor pattern.

## 2. Vendor master data — why one real supplier becomes three SAP vendor records

**The mechanism (this is exactly EMEA's complaint):**
SAP vendor master data is structured in layers: **general data** (name, address, search/match-code) is meant to be shared across the whole client, while **company-code-specific data** (reconciliation account, payment terms, withholding tax, and critically, **tax classification/tax grouping** — tables like LFAT/LFBW) is maintained separately *per company code*. The correct design is one vendor master record extended to multiple company codes. In practice, when company codes are onboarded independently — especially post-acquisition, where each legacy entity had its own SAP (or pre-SAP) instance and its own AP team — the same real-world supplier gets **created from scratch** in each instance/company code rather than extended. Each new record gets its own vendor number, its own tax classification, sometimes its own bank details and payment terms. SAP has no cross-instance identity concept to catch this; within one instance, duplicate-prevention relies on the search/match-code on address data, which is exactly the kind of fuzzy match (name/address variants, language differences, abbreviations) that fails across a 14-language, multi-country supplier base.

Consequence for the case: this isn't a data-quality bug that a smarter AI model fixes — it's a structural artifact of three separate SAP instances each independently onboarding the same suppliers with no shared master. A "same supplier, three tax profiles" problem is not solvable by better invoice coding; it requires an **entity-resolution / supplier-identity layer** sitting above the three SAP instances (matching vendor records across instances by name/address/tax-ID fuzzy match) before any tax determination logic can even ask "what is this supplier's correct tax treatment." This should shape the information model: "supplier" (real-world entity) must be modeled as distinct from and mapped to multiple "vendor master records" (per-instance/per-company-code SAP objects), not treated as 1:1.

Sources: [SAP vendor master account groups](https://drop.maru.tw/beta-post/sap-vendor-master-understanding-account-groups-1767648812), [SAP Community: vendor master duplication](https://community.sap.com/t5/enterprise-resource-planning-q-a/vendor-master-duplication/qaq-p/7770187), [SAP Community: one vendor for two company codes](https://community.sap.com/t5/enterprise-resource-planning-q-a/one-vendor-for-two-company-codes/qaq-p/7035291), [Codasol: vendor master data cleansing / duplicate payments](https://www.codasol.com/vendor-master-data-cleansing-prevent-duplicate-supplier-payments-sap/), [Vertex SAP partner page — vendor classes](https://www.vertexinc.com/partners/sap)

## 3. Confidence-based human-review queues in existing AI/automation tools

Three real, named patterns, all converging on the same shape — **score everything, auto-process high-confidence, route the rest with reasons attached**:

- **Vic.ai (AP invoice processing):** Define confidence thresholds; invoices below the threshold (or outside defined rules) are automatically routed to a human review queue instead of auto-posted. Vic.ai frames this as evolving *away* from a static "exception queue" toward continuous accuracy scoring — the review pool shrinks over time as the model's demonstrated accuracy on a given vendor/pattern rises, and "Autopilot" lets the system take over approval steps once accuracy on that class of transaction is proven.
- **AppZen (invoice/expense audit):** Every transaction gets a **risk score** (their "Compliance Index" concept for expenses, an equivalent risk score for invoices) from a combination of signals; low-risk items auto-approve, high-risk ones are flagged for manual review **with the reasons and supporting documentation attached** — not just "flagged," but flagged with an explanation a human can act on quickly. Reported outcome (AppZen's own marketing numbers, not independently verified): 70–80% of transactions auto-approved, ~90% audit-team time savings.
- **ONESOURCE (Thomson Reuters):** Framed at the compliance/filing layer rather than per-invoice-determination: "built-in validations, reconciliation workflows, variance explanations, audit logs, and assembled review packs that document exceptions, adjustments, and filing evidence." I could not find public documentation of a specific per-transaction confidence score or ML threshold mechanism inside ONESOURCE Determination itself (unlike Vic.ai/AppZen, which are explicit about this) — treat "ONESOURCE has an ML confidence-routing mechanism" as **not verified / not publicly documented**, only that it has structured exception/variance workflows at the compliance layer.

Pattern to reuse for the prototype's exception path: (1) a numeric or tiered confidence signal per determination, (2) auto-proceed above threshold, (3) route below threshold to a queue **carrying the reason/evidence, not just a flag**, (4) treat the threshold as something that should tighten over time as the system proves accuracy on a given supplier/jurisdiction pattern — which maps well onto the Head of Tax Risk's veto and "wrong matters more than slow."

Sources: [Vic.ai FAQ](https://www.vic.ai/frequently-asked-questions), [Vic.ai — AP Automation accuracy as the new exception rate](https://www.vic.ai/blog/ap-automation-why-ai-accuracy-is-the-new-exception-rate), [Vic.ai — how AP Autonomy works](https://www.vic.ai/blog/how-does-vic-ai-ap-autonomy-work), [AppZen — 6 ways AI can improve spend audit](https://www.appzen.com/blog/6-ways-ai-can-improve-your-spend-audit-process), [AppZen — What is AppZen's Compliance Index](https://www.appzen.com/blog/what-is-appzens-compliance-index), [AppZen — fraud and risk detection use case](https://www.appzen.com/use-case-fraud-and-risk-detection), [Thomson Reuters ONESOURCE Determination features](https://tax.thomsonreuters.com/en/products/onesource-determination/features)

## 4. Tenant-boundary AI deployment patterns — resolving "nothing leaves our tenant"

Status: researched (fast pass, web search only). Goal: a concrete, defensible technical answer for how "determine externally" (outside SAP) can still mean "inside Northgate's own tenant boundary" — not a contradiction of the security stakeholder's line.

### 4.1 Azure OpenAI Service provisioned in the customer's own Azure subscription

This is a real, named, current deployment model, not a workaround. The Azure OpenAI *resource* (the control-plane object an application calls) is provisioned inside the customer's own Azure subscription and tenant, not a shared multi-tenant endpoint the vendor operates. Microsoft's enterprise architecture guidance for this shape (Microsoft Learn's "Standard Agent Setup") explicitly combines **bring-your-own (BYO) Azure resources** provisioned in the customer's subscription, **network isolation**, and **private endpoints for all communication** — and calls out dedicated subscriptions/resource groups per tenant as the recommended pattern "for regulated or high-security workloads," which is exactly Northgate's posture.

Data-handling terms specific to this offering, per Microsoft's own documentation:
- Prompts, completions, and embeddings sent to your Azure OpenAI resource are **not sent to OpenAI** (the model originator) and are **not used to train any foundation model**, without the customer's explicit opt-in.
- Data is processed and stored within the **Azure region the customer selects** — a real regional data-residency guarantee, not just a policy statement.
- Prompts/completions are retained up to 30 days for **abuse monitoring** by default (isolated to the customer's subscription, not accessible to other customers, to OpenAI, or to other Microsoft teams) — and Microsoft offers a documented opt-out ("modified abuse monitoring") for eligible customers with sensitive-data use cases, which a tax/financial workload like Northgate's would very plausibly qualify for and should apply for during the security review.
- Full Microsoft enterprise Data Processing Agreement (DPA) coverage applies, giving Northgate's legal/security team a contractual, auditable hook — not just a marketing claim — to point to.

**Important precision point:** "provisioned in your subscription" is a *logical and contractual* isolation boundary, not literal dedicated hardware — the underlying GPU compute is still Microsoft-operated infrastructure in that Azure region. What actually changes tenant-to-tenant is: which subscription owns the resource and its access control, which region the data is pinned to, and the contractual no-training-use commitment. This distinction matters for how the pitch should phrase "nothing leaves our tenant" — see 4.6.

### 4.2 AWS Bedrock — same idea, materially different mechanism

Bedrock is worth naming as the AWS-equivalent option (relevant if Northgate's landing zone is AWS rather than Azure — the SAP-domain research above didn't establish which hyperscaler Northgate runs on, so this should be flagged as an open question / assumption on the assumptions slide). But it works differently from Azure OpenAI in a way worth being precise about, since overclaiming here is exactly the kind of imprecision a technical panel would catch:

- Bedrock is a **fully-managed AWS service**, not a resource that gets deployed inside the customer's own AWS account/VPC compute. The model inference itself runs in AWS-operated "model deployment accounts," one dedicated per model provider — model providers themselves cannot access these accounts.
- What the customer *does* control is network path: **AWS PrivateLink** lets a VPC reach Bedrock via a private VPC endpoint, so requests never traverse the public internet — traffic stays on the AWS network end-to-end.
- Data-use terms: AWS states neither AWS nor third-party model providers use Bedrock inputs/outputs to train Amazon or third-party models, and Bedrock doesn't store or share customer input/output data with model providers.
- Bedrock carries SOC 1/2/3 and the standard AWS ISO certifications (27001, 27017, 27018, 27701, 22301, 20000, 9001).

**Net:** Azure OpenAI's "BYO resource in your subscription" framing is a closer literal match to "nothing leaves our tenant" than Bedrock's "managed service reached via private network path" framing — worth naming explicitly if asked to compare, though both satisfy the same practical outcome (no public internet transit, no training use, contractual data segregation).

### 4.3 Self-hosted open-weight models — not realistic for this engagement, and why

Running Llama, Mistral, or a similar open-weight model entirely on Northgate-owned infrastructure with zero external API calls is the most literal reading of "nothing leaves our tenant," and it's a real, current pattern — but it does not fit this case's constraints:

- Self-hosting shifts the operating model from consumption to ownership: GPU provisioning, a serving engine, model versioning, latency tuning, prompt-drift monitoring, and security patching become the team's job, not the vendor's. Industry guidance pegs the added operational overhead at roughly **15-20% on top of raw infrastructure cost**, and typically requires dedicated MLOps expertise the team may not already have — a cost that's easy to underestimate in planning.
- Cost/volume breakeven guidance: self-hosting becomes financially competitive only at meaningfully high sustained volume (rule-of-thumb figures cited: roughly 2M+ tokens/day to break even; under ~10M tokens/month, a managed API is typically cheaper once operational overhead is counted). Northgate's actual invoice volume is unknown at prototype stage, but "hundreds of thousands of AP transactions a month" is not obviously in open-weight-hosting's favor once the 8-week timeline and 2-engineer team are factored in.
- Accuracy tradeoff: open-weight models are closer to frontier hosted models than commonly assumed on general benchmarks (e.g., Llama 3.1 405B ~88.6% MMLU vs. GPT-4o ~88.7%; Mistral Large 2 ~84%), but this is not the same as validated performance on the specific task here — multilingual (14-language) invoice/tax-document extraction and jurisdiction-specific reasoning — where frontier hosted models have materially more real-world enterprise document-extraction tuning and tooling (structured output, function-calling reliability, vision/OCR quality) than most open-weight deployments, especially self-served with no fine-tuning budget in 8 weeks.
- **Verdict: not realistic for this engagement.** Two engineers, eight weeks, and a security review that hasn't even scoped requirements yet is not the environment to also stand up and operate GPU inference infrastructure from scratch. This is the option to mention and explicitly decline, with the reason above — it demonstrates awareness of the "purest" answer to "nothing leaves our tenant" while making the buildable case for why it's not the right one now.

### 4.4 Private endpoint / VPC-isolated connectivity, generally

Both hyperscalers converge on the same underlying pattern, and it's often what a strict security review is actually probing for when it says "nothing leaves our tenant" at the network level (as distinct from the data-use/training question above):

- **Azure Private Link / private endpoints:** gives the Azure OpenAI resource a private IP inside the customer's VNet; traffic between the application and the resource stays on the Microsoft backbone network and never touches the public internet. Combined with disabling public network access on the resource (Firewalls and Virtual Networks set to fully restrict non-private traffic) and a Private DNS Zone so hostname resolution actually returns the private IP (a common misconfiguration — without it, DNS still resolves to the public IP and traffic bypasses the private path entirely), this is a complete network-isolation configuration, not just a feature flag to turn on.
- **AWS PrivateLink:** the equivalent mechanism for Bedrock — a VPC interface endpoint that keeps invocation traffic within the AWS network rather than routing over the public internet.
- This is a distinct, additive control from the data-use terms in 4.1/4.2 — a security review will likely want both: contractual/architectural guarantee that data isn't used for training or shared with third parties (4.1/4.2), *and* network-level proof that traffic never crosses the public internet (4.4). Treat these as two separate checkboxes in the pitch, not one.

### 4.5 What a vendor security review concretely checks to validate "this really doesn't leave our tenant"

Building on the SIG/CAIQ groundwork already in `security-review-norms.md`, the AI/tenant-isolation-specific layer of that review typically asks for:

- **Architecture and data-flow diagrams** showing every system the data touches, including the LLM call — this is the direct, checkable artifact for the "outside SAP but inside your tenant" claim: a reviewer will want to see the invoice data path traced from SAP (read-only extract) → the determination layer → the model call → back to the human review queue, with every hop labeled as staying inside Northgate's Azure/AWS tenant boundary.
- **Subprocessor disclosure** — does the vendor's own vendor (here, Microsoft/OpenAI or AWS/the model provider) see the data at all, under what terms. This is precisely what 4.1/4.2's "not shared with the model provider, not used for training" language is meant to pre-answer.
- **Network configuration evidence**, not just a claim — reviewers increasingly ask for proof that public network access is actually disabled on the resource (config screenshots, IaC/Terraform showing the private-endpoint-only setup), because "we use Private Link" and "we disabled public access" are two different, both-necessary facts.
- **Contractual backing** — the DPA and any Limited Access / modified-terms application (e.g., Azure's modified abuse-monitoring opt-out) get checked as legally binding artifacts, not marketing pages.
- **Architectural vs. contractual isolation, treated as different questions** — reviewers distinguish "is cross-tenant access technically impossible" (architecture) from "has the vendor promised not to" (contract); a strong answer for Northgate has both — Microsoft's subscription-scoped resource + private endpoint (architecture) plus the DPA and no-training-use terms (contract).
- **SOC 2 Type II and recent pen test results** for the underlying platform (already covered in `security-review-norms.md`) — Azure OpenAI and Bedrock both carry these at the hyperscaler level, which shortens (but doesn't eliminate) this part of the review; the vendor's own application layer on top still needs its own review artifacts.

### 4.6 Recommendation and reconciling "determine externally" with "nothing leaves our tenant"

**Superseded note:** at the time this section was written, the hyperscaler was an open discovery question. It has since been resolved — see `claims.md` ("Hyperscaler confirmed as Microsoft/Azure for planning purposes," RESOLVED per Renata's decision, still ASSUMED in the PIL sense/settled premise, not externally verified). The recommendation below stands; treat "confirm as an early discovery question" language as historical, not current.

**Recommendation: build the determination layer against a hosted frontier model — Azure OpenAI Service, confirmed as the planning assumption — provisioned in Northgate's own subscription, reached exclusively through a private endpoint with public network access disabled, with the abuse-monitoring data retention opted down and the standard DPA in place.** This is the option that is simultaneously (a) buildable by 2 engineers in 8 weeks — it's API integration work, not infrastructure operation, (b) capable of the multilingual, messy-document extraction and reasoning the prototype needs to demonstrate, and (c) a real, literal match for "nothing leaves our tenant": the resource lives in Northgate's subscription, the data is pinned to Northgate's chosen region, it's never used for training, it's not visible to the model provider, and it never transits the public internet. Self-hosting (4.3) is the more literal but operationally unrealistic answer for this timeline; a public multi-tenant API call is the fast but disqualified answer given the enterprise security stakeholder's line — this in-tenant hyperscaler pattern is the buildable middle that actually clears the bar.

**Reconciling the language:** the existing architecture framing in Section 1 — "extract, determine externally, recommend" — should be read and stated explicitly as **"externally to SAP, internally to Northgate's own cloud tenant."** The phrase "determine externally" describes *where in the system architecture* the tax-recovery logic runs (outside SAP's own application layer, since SAP is read-only and can't host custom determination logic or write results back), not a statement about whose infrastructure processes the data. Once the determination layer's LLM calls are shown to run inside a Northgate-owned, private-endpoint-only Azure (or AWS) resource, "external to SAP" and "nothing leaves our tenant" are fully compatible — they're answering two different questions (where does the logic sit relative to SAP vs. whose security boundary contains the data), not competing claims. This reconciliation is exactly the kind of ambiguity the brief instructs to resolve explicitly on an assumptions slide, and it doubles as a strong, technical answer if the panel interrupts to press on it.

**One more precision point worth stating out loud in the pitch, not glossing over:** "nothing leaves our tenant" cannot be interpreted as "zero third-party infrastructure ever touches the data" — even a BYO-subscription Azure OpenAI resource runs on Microsoft-operated shared compute underneath the logical/contractual isolation boundary. The defensible, operational definition to propose to the security stakeholder is: data stays within the customer-owned resource boundary and chosen region, is never used for model training, is never visible to the model provider, and never transits the public internet. That's a checkable, concrete definition a security review can actually validate against evidence (4.5) — which is a better answer in the room than asserting an absolute that isn't technically achievable with any hosted model, open-weight or not, short of air-gapped on-prem hardware.

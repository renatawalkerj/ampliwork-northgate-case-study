## 1. Multi-instance SAP + tax engine integration pattern; what "read-only" rules out

**Standard pattern (Vertex O Series, ONESOURCE Determination, Avalara AvaTax — all three):**
The tax engine sits *outside* SAP and is called synchronously at the pricing/tax-determination step inside a live transaction (PO, goods receipt, AP invoice posting). SAP's pricing procedure is configured to call the external engine via RFC (Vertex's classic connector) or REST/API (modern S/4HANA side-by-side extensibility on SAP BTP), the engine returns a jurisdiction + tax code + rate, and SAP writes that result back onto the document. Vertex explicitly maintains per-company-code data ("vendor classes" — vendor code, vendor name, and the company code/taxpayer the vendor belongs to) so one engine instance can serve multiple SAP company codes with different tax profiles. Thomson Reuters ONESOURCE positions the same way: "single centralized tax engine" fed by "pre-built and certified integrations" per ERP, so multiple SAP instances (or company codes within instances) can all point at one engine without being consolidated first.

Key implication: **you don't need to consolidate the three SAP instances to integrate a tax engine.** The pattern was designed for exactly this — multiple source ERPs, one tax brain. This directly undercuts any framing that treats non-consolidation as a blocker to a unified tax layer; it's a solved integration problem, not a structural one.

**What "read access only, no writes, any version" actually rules out architecturally:**
- Standard tax-engine integrations (Vertex, ONESOURCE) are *transactional* — they intercept a live posting and write the determined tax code back onto the SAP document in real time. That write-back is exactly what's forbidden. So the brief's "AI that reads invoices and tells us the right tax treatment" **cannot be built as a live, in-transaction SAP integration** in v1. It has to be built as a side-by-side/read-only extraction-and-advise layer: pull invoice, PO, goods-receipt, vendor-master data out via read-only APIs/RFC/OData (SAP's own side-by-side extensibility model — BTP consuming stable read APIs via "communication scenarios" configured for read-only access), run determination and recovery logic externally, and surface a recommendation to a human — who then makes the actual correction or claim through whatever channel Northgate already uses (manual SAP entry, the tax engine's own workflow, a filing system). The system never posts anything back into SAP itself.
- No writes also rules out any "auto-fix the vendor master" or "auto-correct the tax code in SAP" remediation — consistent with the Head of Tax Risk's veto and the security team's control posture. Correction has to happen through an existing SAP user with their own write permissions, with the tool's output as a recommendation/audit trail, not an autonomous write.
- This is a reasoned inference from how SAP extensibility/communication-scenario permissioning works, not a documented "read-only tax AI" case study — I did not find a public source describing this exact constraint combination (read-only + multi-instance + tax recovery AI). Treat as ASSUMED architecture logic, not a verified vendor pattern.

## 2. Vendor master data — why one real supplier becomes three SAP vendor records

**The mechanism (this is exactly EMEA's complaint):**
SAP vendor master data is structured in layers: **general data** (name, address, search/match-code) is meant to be shared across the whole client, while **company-code-specific data** (reconciliation account, payment terms, withholding tax, and critically, **tax classification/tax grouping** — tables like LFAT/LFBW) is maintained separately *per company code*. The correct design is one vendor master record extended to multiple company codes. In practice, when company codes are onboarded independently — especially post-acquisition, where each legacy entity had its own SAP (or pre-SAP) instance and its own AP team — the same real-world supplier gets **created from scratch** in each instance/company code rather than extended. Each new record gets its own vendor number, its own tax classification, sometimes its own bank details and payment terms. SAP has no cross-instance identity concept to catch this; within one instance, duplicate-prevention relies on the search/match-code on address data, which is exactly the kind of fuzzy match (name/address variants, language differences, abbreviations) that fails across a 14-language, multi-country supplier base.

Consequence for the case: this isn't a data-quality bug that a smarter AI model fixes — it's a structural artifact of three separate SAP instances each independently onboarding the same suppliers with no shared master. A "same supplier, three tax profiles" problem is not solvable by better invoice coding; it requires an **entity-resolution / supplier-identity layer** sitting above the three SAP instances (matching vendor records across instances by name/address/tax-ID fuzzy match) before any tax determination logic can even ask "what is this supplier's correct tax treatment." This should shape the information model: "supplier" (real-world entity) must be modeled as distinct from and mapped to multiple "vendor master records" (per-instance/per-company-code SAP objects), not treated as 1:1.

## 3. Confidence-based human-review queues in existing AI/automation tools

Three real, named patterns, all converging on the same shape — **score everything, auto-process high-confidence, route the rest with reasons attached**:

- **Vic.ai (AP invoice processing):** Define confidence thresholds; invoices below the threshold (or outside defined rules) are automatically routed to a human review queue instead of auto-posted. Vic.ai frames this as evolving *away* from a static "exception queue" toward continuous accuracy scoring — the review pool shrinks over time as the model's demonstrated accuracy on a given vendor/pattern rises, and "Autopilot" lets the system take over approval steps once accuracy on that class of transaction is proven.
- **AppZen (invoice/expense audit):** Every transaction gets a **risk score** (their "Compliance Index" concept for expenses, an equivalent risk score for invoices) from a combination of signals; low-risk items auto-approve, high-risk ones are flagged for manual review **with the reasons and supporting documentation attached** — not just "flagged," but flagged with an explanation a human can act on quickly. Reported outcome (AppZen's own marketing numbers, not independently verified): 70–80% of transactions auto-approved, ~90% audit-team time savings.
- **ONESOURCE (Thomson Reuters):** Framed at the compliance/filing layer rather than per-invoice-determination: "built-in validations, reconciliation workflows, variance explanations, audit logs, and assembled review packs that document exceptions, adjustments, and filing evidence." I could not find public documentation of a specific per-transaction confidence score or ML threshold mechanism inside ONESOURCE Determination itself (unlike Vic.ai/AppZen, which are explicit about this) — treat "ONESOURCE has an ML confidence-routing mechanism" as **not verified / not publicly documented**, only that it has structured exception/variance workflows at the compliance layer.

Pattern to reuse for the prototype's exception path: (1) a numeric or tiered confidence signal per determination, (2) auto-proceed above threshold, (3) route below threshold to a queue **carrying the reason/evidence, not just a flag**, (4) treat the threshold as something that should tighten over time as the system proves accuracy on a given supplier/jurisdiction pattern — which maps well onto the Head of Tax Risk's veto and "wrong matters more than slow."

Sources: [Vic.ai FAQ](https://www.vic.ai/frequently-asked-questions), [Vic.ai — AP Automation accuracy as the new exception rate](https://www.vic.ai/blog/ap-automation-why-ai-accuracy-is-the-new-exception-rate), [Vic.ai — how AP Autonomy works](https://www.vic.ai/blog/how-does-vic-ai-ap-autonomy-work), [AppZen — 6 ways AI can improve spend audit](https://www.appzen.com/blog/6-ways-ai-can-improve-your-spend-audit-process), [AppZen — What is AppZen's Compliance Index](https://www.appzen.com/blog/what-is-appzens-compliance-index), [AppZen — fraud and risk detection use case](https://www.appzen.com/use-case-fraud-and-risk-detection), [Thomson Reuters ONESOURCE Determination features](https://tax.thomsonreuters.com/en/products/onesource-determination/features)

## Gaps / what I could not verify in a fast pass

- No public documentation found of a named tax-tech tool doing confidence-based routing at the specific "is this VAT recoverable" determination level (as opposed to invoice-audit/AP-fraud risk scoring, which is well documented). The prototype's exception logic will need to be your own design, grounded in the Vic.ai/AppZen pattern but applied to a determination ONESOURCE/Vertex themselves don't visibly automate this way.
- Exact SAP table/transaction names (LFAT, LFBW, OBD3) are standard FI references surfaced by search, not independently confirmed against SAP help docs.
- No case study found combining all three constraints at once (multi-instance + strictly read-only + tax-recovery AI) — the "read-only rules out live tax-engine write-back" conclusion above is architectural reasoning from how SAP extensibility permissioning works, not a documented precedent.

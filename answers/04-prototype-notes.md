It would address the APAC analyst's specific complaint, but it's a supplier-communication workflow system, not a tax-determination system — a different build outside the brief's stated ask and the 2-engineer/8-week budget. One thing that surprised us while building it — leading candidate, pending the actual build: a capable model's default behavior is to trust whatever single vendor record it's handed rather than spontaneously checking for contradicting records elsewhere — the EMEA manager's failure mode isn't solved "for free" by using a capable model, it required an explicit design decision (look up every vendor record for the same real-world supplier before finalizing). See `prototype/evals/eval-plan.md` section 3's worked example.
3. Which messy input the demo handles — **answered: not one, five, but with one flagship.** Duplicate-vendor-with-conflicting-tax-profiles (INV-1002) is the flagship, tied directly to the EMEA manager's unprompted complaint. Alongside it: a clean happy-path case (INV-1001), a format-compliance failure (INV-1003, Germany's *leistungsdatum* trap), an urgency-queue-jump case (INV-1004, Italy's tight window beating higher-confidence-but-less-urgent items), and a genuine tax-judgment ambiguity unrelated to data quality (INV-1005, needs a contract the invoice doesn't carry). See `prototype/data/invoices.json` and `prototype/README.md`'s build breakdown for the full set and which are must-build vs. should-build.
